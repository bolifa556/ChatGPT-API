# 原生生图与自定义 API 路由修复

版本：3.0.3。日期：2026-09-30。

## 原因与修复

原生 Images 客户端使用专用生图模型，而聊天模型菜单没有列出 `gpt-image-2`。原兼容通道先按聊天目录检查模型，导致生图请求在本地返回 `Unknown model`，未到达官方服务。

新增独立 Images 通道，不改原生客户端、不修改账号登录或聊天正文。官方 `/images/generations`、`/images/edits` 请求原样发送；只有转到 API 时才选择 API 生图模型并做必要格式适配。不会把这些请求送入聊天的 Responses / Chat 转换器。

| 状态 | 路由与结果 |
| --- | --- |
| 有官方登录，官方可用 | 官方 Images 接口，保留原生请求、响应及图片元数据。 |
| 有官方登录，官方明确不可用 | 选择 API 生图或编辑模型；没有对应模型或候选全部不可用则报错。 |
| 无官方登录，或 Linux provider-only | 直接使用 API 生图或编辑模型，不向官方发起生成请求。 |
| 网络失败、临时限流、服务器故障 | 保留错误，不重新生图，不增加网络重试。 |
| 内容拒绝、请求参数错误、已接受但结果格式错误 | 保留错误，不通过另一个通道重新生成。 |

API 模型不限于 GPT Image。优先使用网关能力元数据，也可识别常见生图名称；无元数据的任意别名可用 `IMAGE_MODEL` / `IMAGE_EDIT_MODEL` 指定，必须存在于该 API 的模型列表。默认 JSON 编辑；仅支持旧式上传的网关可以配置 multipart。URL 图片结果读取真实图片转成原生 base64；图片下载不发送 API Key 或官方账号凭据。配置细节见 [配置说明](configuration.md#生图与编辑)。

## 验证证据与边界

- 原生内置 `imagegen` 已实际生成中文 ChatGPT-API 流程图。生产路由记录：`official images operation=generations model=gpt-image-2 status=200`。修复前相同专用模型返回本地 400。
- `tests/image-generation-test.mjs` 的 15 项受控检查全部通过：官方原样转发、编辑、无登录、任意生图别名、OAuth 隔离、URL 转 base64、旧式上传、官方文件引用、失败边界、配额回退、候选不可用和无模型报错。
- 原有 8 组协议回归全部通过，包含 225 组跨模型协议组合；Windows 启动器与独立发布包测试通过。真实登录与原生配置的内容校验在测试和路由更新前后相同。
- 使用真实网关模型列表验证 provider-only：14 个模型，生图模型为 0，返回 HTTP 400 / `no_gateway_image_model`，官方通道禁用。没有向真实网关提交生成请求。
- 由于真实网关目前没有生图模型，自定义生图成功路径、官方不可用后的 API 回退，以及编辑成功路径使用受控端点验证；不把它们写成真实模型生成成功。
- Windows x64、Linux x64 / ARM64 的 3.0.3 发布包均包含同一图片适配模块；清单和逐文件 SHA-256 校验通过。ARM64 包做静态架构与完整性校验，不声称在 ARM64 客户端上实测。
- Linux x64 发布包在 Ubuntu 22.04 / WSL 隔离目录实际执行：同样的 15 项生图协议检查和 8 项 provider 安装/运行检查全部通过，包含生图别名及编辑格式配置保留。未启动 Linux 原生桌面 GUI，也未向真实 API 提交生图请求。

本次没有改变网络策略、推理档位、模型本身的能力或原生客户端支持范围。
